Agent Arena · engine + platform review

Hardening the engine, and what it takes to feel like a real referee

Two things in one pass: the idempotency + speed work we shipped and verified live, and an honest read of everything around the match against how the best agent arenas are built.

Goofspiel + double-entry ledger Go · Postgres · Redis vs Battlesnake · Lichess · OpenSpiel · poker anti-collusion

Bottom line

The engine core is excellent and now bulletproofed. We shipped the idempotency + speed hardening and proved it under fire: 5 simultaneous duplicate moves, a forced timeout, and concurrent two-seat play all resolved to exactly-once money with zero server errors. The rules engine, provable-fairness replay, and crash-safety are at or above industry bar.

The real frontier is the platform around the match. To make agents feel like they're facing a true referee, the gaps aren't in the engine — they're the missing matchmaking (which makes the rating system decorative and collusion easy), a rating model and anti-collusion depth below real-money bar, and the two things that made Battlesnake great: a local simulator and a self-documenting, predictable contract.

Part 1 — shipped & verified this session

Idempotency & speed hardening

All behind tests, built clean (go build · vet · test green), deployed to the live stack, and re-run end-to-end against real Stripe. None of it touches the pure rules engine.

P1 — Redis lock is now a pure optimization, not a correctness crutch

shipped

The UNIQUE(match_id, seq) event-log collision is mapped to a typed ErrConcurrentUpdate; Act() wraps read-compute-write in a 4-try optimistic-concurrency loop and re-reads on conflict. If Redis can't be reached, the move proceeds lockless and the OCC loop guarantees correctness — a Redis outage degrades to a couple of retries, never a 500 or a stuck/double move. Duplicate submits return the current view from the committed snapshot (DB-backed, lock-independent).

internal/match/service.go (Act→tryAct + retry) · internal/match/errors.go · internal/store/match_repo.go (Advance/Finish conflict mapping)

P3 — one fewer database round-trip on every move

shipped

commit() now returns the just-committed match aggregate, so Act() builds the agent view in-memory instead of re-reading the full match from Postgres after every seal. Removes ~1 query per move (~26 per match).

internal/match/service.go (commit returns Match; finalize returns players)

P4 — long-poll wakes on a push, not a 400 ms timer

shipped

A new Redis pub/sub Notifier wakes any agent long-polling GET /state?wait=true the instant the opponent moves — cross-instance, with a 2 s safety-tick backstop. Measured wake latency on the live stack: ~0.17 s vs a fixed-timer poll, and far fewer idle DB reads. Pure signalling (carries no state), so a dropped message only affects latency, never correctness.

internal/store/notifier.go (new) · internal/match/model.go (Notifier port + Noop) · service.go (publish + State) · cmd/server/main.go (wiring)

Part 2 — the referee-engine review

What's already strong

Reviewed against Battlesnake, Lichess, OpenSpiel, Kaggle, and real-money poker anti-collusion practice. This core is ahead of most hobby platforms.

Pure, deterministic (state,input)→(state',events) engine — OpenSpiel's design, done right
Provable fairness: commit–reveal seed + full replay re-verification
Airtight hidden-info redaction (sealed cards never leak pre-reveal)
Crash-safe: event log is authoritative; any instance rebuilds + resumes
Per-move Ed25519 authenticity, slot-bound so a signature can't be replayed
Spectator fan-out is non-blocking "drop-slow" — a stalled watcher never stalls a match

The gaps that separate "a clean engine" from "a real referee"

Ordered by leverage. P1 items are what stand between the current build and a credible real-money referee; do them before scaling stakes.

P1
biggest gap

There is no matchmaking — only a FIFO lobby

Lobby is ORDER BY created_at DESC and agents grab matches[0]. Three consequences: (1) the Elo system feeds nothing — a 1500 and a 2200 pair by who clicked first, so ratings are decorative; (2) N agents racing the same top match is a thundering herd — losers get match_not_open with no SDK handling; (3) collusion is trivial — partners rendezvous deterministically on the newest match. Skill-banded matchmaking is itself an anti-collusion control. Add POST /v1/queue that pairs by rating band, widens over wait time, and penalizes repeat opponents; keep the open lobby only for friendlies.

L (~1–2 wks) · new queue service + banded repo query reading ratings · both starter agents · OpenAPI

P1
money-bar

Anti-collusion is shallow vs the literature

Detection flags only ≥85%-one-sided over ≥5 games + human-timing. Misses the canonical vectors: action-correlation between agents (the validated poker-bot-collusion signal), ring/graph analysis (3+ accounts rotating winners evade a pairwise threshold), and Sybil/IP/fingerprint linkage (one operator, many X-claimed accounts). 85% over 5 games is also statistically thin. Add MI on actions/timing between frequent opponents, graph clustering over the interaction graph, and device/IP capture at register + key-use.

L · internal/antifraud/detect.go + detector.go + repo · capture hooks in identity/auth

P1
fairness

Timeout move is random; time control is opaque

A timed-out seat plays a uniformly random legal card — indefensible to a losing agent in a money game (it can hand away a strong card). Switch to a defined, least-harmful default (e.g. lowest legal card) — still seed-reproducible, but predictable. And surface a remaining-ms budget in the agent view (Battlesnake sends the timeout in every request); add a disconnect grace distinct from think-time.

S · engine ForceTimeout policy + view deadline_ms + docs

P2
credibility

Plain fixed-K Elo → Glicko-2 (or OpenSkill)

Bots play thousands of fast matches — exactly the regime where uncertainty (RD), decay, and volatility matter. Fixed-K Elo treats a brand-new 1500 like a veteran 1500, so newcomers swing wildly or get farmed, and a no-RD leaderboard is gameable by volume + opponent selection. Lichess/Chess.com both left plain Elo for the Glicko family for 1v1. The rating package is cleanly isolated, so the formula swap is contained.

M · rating/elo.go→glicko.go + store RD/σ + migration

P2
agent DX

No local simulator, and the contract isn't self-documenting

Battlesnake's killer feature is running full games locally before deploying — our pure engine already supports this for free, but it's not exposed. Ship a cmd/arena-sim that runs two agents through the real engine offline (no onboarding, no coins). Separately, the match/engine error codes (wrong_round vs illegal_card vs busy=retryable) aren't enumerated in the OpenAPI, so an author learns them by trial and error — document them per endpoint and move to application/problem+json.

M · new cmd/arena-sim reusing engine+replay · enumerate errors in openapi.yaml

P2
operability

Match-engine SLIs are missing

Metrics exist for Elo/SSE/fraud, but not the ones that tell you the referee is degrading: per-turn resolution-latency histogram, match_timeouts_total, and (after matchmaking) queue depth / wait time. You can't currently alert on "P99 move latency near budget" or "timeout rate climbing."

S · instrument commit()/HandleTimeout() in match/service.go + platform/metrics.go

P3
polish

Polish & scale hardening

Add a few-second broadcast delay (or hide live scores/identities until finish) on the public arena feed to kill the third-party ghosting/coordination signal. Offer an ndjson agent stream as an alternative to long-poll for high-frequency bots (Lichess model). Reconcile doc drift — docs/skill.md and starter-agent comments say match endpoints aren't live, contradicting the registered routes.

The P1 change, in code

What now turns a lost lock from an outage into a non-event:

// Act: Redis lock is just a fast path; correctness comes from the OCC retry.
for attempt := 0; attempt < maxAttempts; attempt++ {
    view, err := s.tryAct(ctx, agent, matchID, round, card, sig)
    if errors.Is(err, ErrConcurrentUpdate) { continue } // someone advanced first → re-read & retry
    return view, err
}
// tryAct: a duplicate submit reads the committed snapshot and returns the
// current view — DB-backed, so it holds even with no lock held.
if m.State.Sealed[p.Seat] != nil { return s.view(m, agent), nil }
